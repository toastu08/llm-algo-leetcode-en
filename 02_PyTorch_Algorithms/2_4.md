# Group 2.4: Supervised Fine-Tuning and Adaptation

This group first judges whether model parameters need to be updated, then checks data, supervision target, parameter update, evaluation, and saving in order; when length or memory constraints appear, long-context or parameter-efficient adaptation methods are added. [2.3](./2_3.md) explains general backpropagation and parameter updates, and this group applies them to SFT; when gradients, the update clock, or training state are abnormal, return to 2.3, while data, template, parameter-scope, and behavior-quality issues stay in this group.

## Learning Path

- First read [33](./33_Fine_Tuning_Readiness.ipynb) to judge whether the problem needs a parameter update; after deciding to enter SFT, check the data and supervision target.
- The basic order is [32](./32_Data_Engineering_for_SFT.ipynb) → [13](./13_SFT_Training_Loop.ipynb) → [15](./15_End_to_End_Fine_Tuning_Experiment.ipynb), determining the data, supervised loss, and training process in turn; when real demonstrations are insufficient, use [PT-SYNTHETIC-DATA](./PT-SYNTHETIC-DATA_Instruction_Generation_and_Verifier_Admission.ipynb) after 32 to generate and verify candidates, then return to 32 to run the final split audit.
- When using LoRA, [13](./13_SFT_Training_Loop.ipynb) determines the supervision target, [14](./14_LoRA_Tutorial.ipynb) restricts the trainable parameters, and training then runs in [15](./15_End_to_End_Fine_Tuning_Experiment.ipynb); when rank, scaling, and variants need to be compared, read [31](./31_LoRA_Variants_Theory.ipynb).
- When truncation, supervision retention, or cross-sample concatenation becomes a problem, after [32](./32_Data_Engineering_for_SFT.ipynb) and [13](./13_SFT_Training_Loop.ipynb), enter [30](./30_Long_Context_Fine_Tuning.ipynb).
- Follow-up learning: after completing data, loss, and the training process, enter [2.5](./2_5.md) to learn preference- and reward-driven updates; when checking formulas across pages, use the [post-training formula index](../topic_discussion/post_training_optimization/formula_reference.md).

## Project Validation Order

After fixing the model, data, and budget, first use 64 to check the training data, then choose 63 or 65 according to memory and the training method, and finally use 62 to execute training, recovery, and evaluation. For execution configuration see [2.10](./2_10.md); for the current experiment status and re-measurement labels see the [post-training optimization experiment asset table](../topic_discussion/post_training_optimization/experiment_assets.md).

| Project | When to enter | Direct input | Main output | Validation content |
|:---|:---|:---|:---|:---|
| [64 SFT Data Quality](./64_SFT_Data_Quality_Project.ipynb) | Raw data preparation entering the pre-training stage | Data version, template, and independent evaluation split | Data admission manifest, sample and split hashes | Deduplication, contamination, template, and split |
| [63 LoRA Variant Comparison](./63_LoRA_Variants_Benchmark.ipynb) | Parameter-efficient fine-tuning is adopted by default and the update scope or rank must be chosen | 64's data admission manifest | LoRA selection manifest and usable adapters | Update scope, rank, memory, and quality |
| [65 QLoRA Selection](./65_QLoRA_Selection_Project.ipynb) | Memory or batch capacity is still constrained after freezing the base model | 64's data admission manifest | QLoRA pairing results, adapter hashes, and run manifest | Compatibility of the quantized base and the adapter |
| [62 SFT Training Delivery](./62_Instruction_Fine_Tuning_Project.ipynb) | The data and parameter-update plan have been determined | 63 or a compatible 65 run manifest | checkpoint, adapter, recovery records, evaluation report, and delivery manifest | Training, recovery, evaluation, and delivery |
